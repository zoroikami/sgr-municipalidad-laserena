1. Objetivo de la entrega 
La entrega tiene por objetivo consolidar el análisis y diseño técnico de la solución antes de avanzar a etapas de 
integración y desarrollo completo. Se evaluará la coherencia entre la planificación del proyecto, los requisitos, los 
modelos UML, el diseño de datos y el prototipo funcional. 
 
Criterio transversal de coherencia 
Los artefactos no deben presentarse como piezas aisladas. Debe existir trazabilidad entre requerimientos, casos 
de uso, clases, entidades de base de datos y pantallas del mockup, cuando corresponda. 
 
2. Condiciones generales de entrega 
• Formato del informe: utilizar el presente formato institucional y mantener una estructura ordenada por secciones. 
• Repositorio Git:  incorporar el enlace al repositorio y asegurar acceso al docente. El repositorio debe contener el 
mockup funcional y, de ser posible, los archivos editables de los diagramas. 
• Legibilidad: todos los diagramas deben insertarse con resolución sufi ciente para leer actores, relaciones, atributos, 
claves y cardinalidades. 
• Identificación: usar códigos consistentes para requisitos y casos de uso, por ejemplo RF-01, RNF-01, CU-01, CU-02, 
etc. 
• Evidencias: incluir capturas del Planner/Jira y del mockup, además de los enlaces correspondientes. 
• Consistencia: nombres de módulos, entidades, actores y funciones deben mantenerse homogéneos en todos los 
artefactos. 
3. Alcance del mockup funcional 
En esta etapa el prototipo se evaluará por navegación, fluidez de interfaces, distribución de elementos, validación 
de campos y uso apropiado de librerías externas. No se exige integración con base de datos ni consumo de API 
para esta entrega.

4. Entregables obligatorios 
4.1 Planner / Jira 
 
Se debe presentar la planificación operativa del proyecto en Planner o Jira. La evidencia debe permitir comprender qué se 
construirá, quién es responsable y cuál es el estado de avance. 
 
• Backlog del proyecto organizado y priorizado. 
• Épicas y/o módulos principales del sistema. 
• Historias de usuario, tareas o actividades asociadas a cada épica. 
• Responsables asignados por tarea o historia. 
• Estados de trabajo claramente diferenciados, por ejemplo: Por hacer, En desarrollo, En revisión y Finalizado. 
• Fechas, hitos o sprint cuando la herramienta y la metodología utilizada lo permitan. 
• Prioridad y dependencias relevantes entre tareas. 
• Captura del tablero y enlace directo al Planner/Jira cuando sea posible. 
 
4.2 Diagramas de requerimientos 
 
Se deben presentar diagramas que pe rmitan visualizar y relacionar los requerimientos del sistema. La notación puede 
ajustarse a la herramienta utilizada, pero debe ser clara y trazable. 
 
• Identificar requerimientos funcionales (RF) y no funcionales (RNF) mediante códigos únicos. 
• Relacionar requerimientos con actores, módulos o procesos del sistema. 
• Mostrar dependencias, agrupaciones o relaciones entre requisitos cuando corresponda. 
• Mantener concordancia con el diagrama general de casos de uso y con los casos de uso específicos. 
• Evitar requerimientos ambiguos; cada requisito debe representar una necesidad verificable.

5. Modelado de casos de uso 
5.1 Diagrama de caso de uso general 
 
Debe existir un diagrama general que represente el sistema completo a nivel funcional, identificando sus principales actores 
y servicios. 
 
• Límite o frontera del sistema claramente identificado. 
• Actores principales y secundarios correctamente nombrados. 
• Casos de uso principales del sistema, sin detallar flujos internos. 
• Relaciones actor–caso de uso y uso adecuado de «include», «extend» o generalización cuando corresponda. 
• Correspondencia con los requerimientos funcionales definidos. 
 
5.2 Casos de uso específicos con especificación – mínimo 10 
 
Se deben entregar como mínimo diez (10) casos de uso específicos. Cada caso debe incluir su diagrama específico y una 
ficha de especificación textual completa. 
 
Condición mínima 
Se exigen al menos 10 casos de uso específicos. Si se presentan menos de 10, el criterio correspondiente quedará 
en nivel “Insuficiente”, con un máximo de 7/20 puntos.

6. Diseño orientado a objetos y datos 
6.1 Diagrama de clases 
 
El diagrama de clases debe representar la estructura lógica del software y evidenciar cómo se organizan las 
responsabilidades principales del sistema. 
 
• Clases del dominio y/o componentes relevantes del sistema. 
• Atributos significativos con tipo de dato cuando corresponda. 
• Métodos u operaciones principales relacionados con las responsabilidades de la clase. 
• Visibilidad de atributos y métodos (+, -, #) cuando se utilice UML formal. 
• Asociaciones con multiplicidades. 
• Herencia, composición o agregación solamente cuando exista justificación en el diseño. 
• Nombres coherentes con los casos de uso y con el modelo de datos. 
 
6.2 DER – Diagrama Entidad–Relación para MySQL 
 
El DER debe mostrar cómo se almacenará la información persistente del sistema en MySQL. Debe ser consistente con el 
script SQL entregado. 
 
• Entidades o tablas correctamente nombradas. 
• Clave primaria (PK) definida para cada tabla que lo requiera. 
• Claves foráneas (FK) y relaciones entre tablas. 
• Cardinalidades 1:1, 1:N y N:M representadas correctamente. 
• Tablas asociativas para resolver relaciones N:M cuando corresponda. 
• Atributos/campos relevantes y tipos de datos compatibles con MySQL. 
• Restricciones básicas y diseño orientado a evitar redundancias innecesarias. 
 
Validación de consistencia 
Toda FK representada en el DER debe existir en el script SQL. Del mismo modo, las tablas creadas en el script 
deben corresponder al modelo presentado en el informe.

7. Implementación inicial 
7.1 Script de base de datos MySQL 
 
Se debe entregar un archivo .sql ejecutable que permita crear la estructura de base de datos diseñada. 
 
• Creación de la base de datos o selección explícita del esquema. 
• Sentencias CREATE TABLE ordenadas correctamente. 
• Definición de PK y FK. 
• Tipos de datos apropiados para los campos. 
• Restricciones como NOT NULL, UNIQUE, DEFAULT u otras cuando corresponda. 
• Índices adicionales si el diseño los justifica. 
• Datos de prueba (INSERT) opcionales, pero recomendados para demostrar estructura y relaciones. 
• El script debe ejecutarse sin errores de sintaxis ni errores de integridad referencial. 
 
7.2 Template / Mockup funcional en Git 
 
El prototipo debe estar implementado y versionado en un repositorio Git. Debe permitir recorrer las principales pantallas y 
demostrar el diseño de interacción previsto. 
 
• Navegación funcional entre pantallas o vistas principales. 
• Flujo de interfaz comprensible y consistente. 
• Distribución adecuada de elementos visuales y formularios. 
• Validación de campos obligatorios, formatos y mensajes básicos al usuario. 
• Uso de librerías externas cuando aporten al diseño o funcionalidad. 
• Código organizado y almacenado en el repositorio Git. 
• README con descripción del proyecto, tecnologías utilizadas e instrucciones para ejecutar el mockup. 
• Enlace del repositorio incorporado en el informe. 
 
Importante 
Para esta entrega no se evaluará conexión con base de datos ni consumo de API. El foco está en la experiencia 
de navegación, consistencia visual, validaciones y estructura del prototipo.
